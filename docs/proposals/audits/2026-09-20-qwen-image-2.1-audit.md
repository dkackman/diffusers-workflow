## Model identity and scope

- **Repo**: `Qwen/Qwen-Image-2.1`. Weights public, **not gated** (`gated: false`), 33.1 GB total in bf16.
- **Parameters**: 7B in the visual generator — 32 single-stream DiT layers with block-causal
  attention (`(q_idx >= kv_idx) or same_image_block`). Plus a **Qwen3-VL 8B** text encoder that
  also does the vision encoding, and a 64-channel RGBA VAE at 16× spatial compression.
  Per-file bf16 sizes from the HF API: `text_encoder` 17.53 GB, `transformer` 14.23 GB,
  `vae` 1.35 GB.
- **License**: **Qwen Research License Agreement**, effective 2026-09-20 — *non-commercial only*,
  requires "Built with Qwen" attribution, commercial use needs a separate grant. This is a
  **hard break from every sibling**, all of which are Apache-2.0. Anything shipped in the catalog
  should say so in the workflow `description`.
- **Pipeline class**: `diffusers.QwenImage21Pipeline`, in `diffusers/pipelines/qwenimage21/`.
  **Already present in the repo's venv** (diffusers `0.41.0.dev0`), imports cleanly, and the
  diffusers `main` docs page for it exists. **No engine work and no diffusers bump is needed.**
  One caveat: the vendor asks for `transformers>=5.17`; the venv has **5.16.1**. `Qwen3VLForConditionalGeneration`
  and `Qwen3VLProcessor` both import successfully on 5.16.1, but this is untested against a real load.
- **Unified, not split.** One pipeline does text-to-image *and* editing: `image=` (a PIL image or a
  **list of up to 10**) turns the same call into conditioned generation. There is no separate
  `QwenImage21EditPipeline`. Components for a dw workflow are `scheduler`, `vae`, `text_encoder`,
  `processor`, `transformer`.
- **Native RGBA.** The VAE decodes 4 channels and `VaeImageProcessor.numpy_to_pil` hands back a
  4-channel `PIL.Image` (`Image.fromarray` on a 4-channel array → mode RGBA), so transparency
  survives to `Result.save` — but **only if saved as PNG**. `dw/result.py` handles `image/png`;
  the existing templates all use `image/jpeg`, which would silently flatten the alpha. This is a
  real template-design constraint.

**Qwen-Image-2.1 supersedes the older line in practice** — it is a new architecture (single-stream
DiT, Qwen3-VL encoder, RGBA VAE) at roughly **half** the weight footprint, and it folds
`Qwen-Image` + `Qwen-Image-Edit` + `Qwen-Image-Edit-Plus` into one checkpoint. But it does **not
retire** them: the older ones stay Apache-2.0 and keep the large ecosystem (Lightning LoRAs, GGUF
builds, ControlNets) that 2.1 has none of yet. They coexist, and the licence is the reason a user
might still want the 20B.

### Where this differs from `docs/proposals/qwen-image-wan-onboarding.md` (draft 2026-09-08)

The draft predates this release by 12 days and is about the **20B Qwen-Image**. Explicitly:

1. **Scale.** Draft: "Qwen-Image (20B)… bf16 doesn't fit; 4-bit BitsAndBytes brings it to ~17GB."
   2.1 is 7B + an 8B encoder = 33.1 GB bf16 — still doesn't fit 24 GB resident, but model
   *offloading alone* plausibly suffices; 4-bit may not be needed at all.
2. **Split vs unified.** Draft: "`QwenImagePipeline` / `QwenImageEditPipeline`… Qwen-Image-Edit is
   the piece that would carry real shape decisions… the reason a skill might be worthwhile."
   In 2.1 there is **one** pipeline; editing is an argument, not a checkpoint. The skill question
   changes shape entirely — see Assessment.
3. **Guidance.** Draft assumes the FLUX/Z-Image flat `guidance_scale` shape. 2.1 takes **no**
   `guidance_scale` at all — only `true_cfg_scale`, defaulting to **1.0 (off)**. A template that
   copies `workflows/templates/text-to-image`'s shape verbatim with a `guidance_scale` argument
   would raise.
4. **Text encoder.** Draft: "The Qwen2.5-VL text encoder is large — quantize it or group-offload
   it (`"text_encoder.model"` with `leaf_level`)" (also in `docs/RECIPES_24GB.md` line 35).
   2.1 uses **Qwen3-VL 8B**, and that encoder also consumes the condition images, so it cannot
   simply be swapped for a remote/quantized text-only encoder.
5. **License.** The draft assumes nothing; 2.1 being research-only is new and material.
6. **RGBA and ≤10 references** are capabilities the draft does not contemplate at all.
7. **Resolution.** Draft assumes the 1024-class default. 2.1 is a **native 2K** model.

`docs/RECIPES_24GB.md` lines 33-37 stay correct **for the 20B model** and should not be edited to
describe 2.1; 2.1 wants its own entry.

## Hardware / quantization fit

**Vendor's own note is thin**: the only memory advice in the entire README is
`pipe.enable_model_cpu_offload()` "for GPUs with limited memory". No VRAM table, no minimum.
The diffusers source states no footprints either. So the arithmetic below is mine, from the HF
blob sizes — reliable for weights, silent about activations.

- **bf16 resident: 33.1 GB. Does not fit 24 GB.** (17.53 + 14.23 + 1.35.)
- **`offload: "model"` (the vendor's `enable_model_cpu_offload`)**: `model_cpu_offload_seq` is
  `"text_encoder->transformer->vae"`, so peak weight residency is the largest single component,
  **17.5 GB** (the text encoder), leaving ~6 GB for activations on a 24 GB card. This is the
  vendor-endorsed path and is the one a first template should take.
  **Untested at 2048×2048**: the target latent grid at 2K is 128×128 = 16 384 tokens, plus the
  Qwen3-VL prefix and (in editing) up to ten condition-image blocks. Attention activations at that
  sequence length are not something I can size from documentation.
- **`offload: "sequential"`** would drop peak weight residency much further at a large speed cost —
  and on MPS the repo downgrades it to `"model"` anyway (`place_component`).
- **4-bit / GGUF**: **nothing exists yet.** There is no `diffusers/Qwen-Image-2.1-bnb-4bit`
  analogous to `diffusers/FLUX.2-dev-bnb-4bit`, and no community GGUF. Every GGUF result the
  search returned is for **Qwen-Image / 2512**, i.e. the 20B — do not carry those claims over.
  A bnb-4bit `text_encoder` component following `workflows/models/flux2-dev.json`'s pattern
  would have to be quantized on the fly via `config_objects.py` rather than pulled pre-quantized.
- FP8 is mentioned only as a vLLM-Omni / SGLang feature, not a diffusers one.
- AMD ROCm and FlagOS multi-chip are claimed; MPS is not mentioned anywhere by the vendor.

## Recommended inference settings

Vendor defaults (README "Default Parameters" table + diffusers docs, in agreement):

| Setting | Value | Source |
|---|---|---|
| `num_inference_steps` | **40** | README table; also the diffusers `__call__` default |
| `width`/`height` | **2048 × 2048** | README table ("Native 2K resolution") |
| `true_cfg_scale` | **1.0 — guidance off** | diffusers default; docs: "Qwen-Image 2.1 is meant to be sampled without guidance, hence the default of 1.0" |
| `guidance_scale` | **does not exist** | `__call__` signature has no such parameter |
| `negative_prompt` | pointless unless `true_cfg_scale > 1`; the pipeline logs a warning either way if the two disagree | source lines ~669-679 |
| dtype | `torch.bfloat16` | every vendor example |
| scheduler | `FlowMatchEulerDiscreteScheduler` with dynamic shift (`mu` from `calculate_shift`, base_shift 0.5 / max_shift 1.15) | source + architecture section |
| `use_kv_cache` | `True` (prefix KV reuse; big win for multi-reference editing) | source; note it changes the *sample*, not just the speed — "Fix a sample by fixing this flag" |
| `output_resolution` | diffusers default **1024** | source — **conflicts with the card's 2048 in effect**: omit width/height and you get a 1024 image, not the recommended 2K |

**Note that conflict.** The diffusers `output_resolution` default of 1024 means a template that
does not pass `width`/`height` silently renders at half the vendor-recommended resolution. A
template should set them explicitly.

**Aspect ratios** (README dict; all values are multiples of 32, which is what the pipeline enforces
via `multiple_of = vae_scale_factor * 2 = 32`, floor-rounding anything off-grid):

```
1:1 (2048,2048)  4:3 (2400,1792)  3:4 (1792,2400)  3:2 (2528,1696)
2:3 (1696,2528)  16:9 (2752,1536) 9:16 (1536,2752)
```

This is a **32-pixel grid constraint**, analogous to H3's `17n+5` and LTX's `8k+1`, and it
**floors** rather than raising — so it belongs in `variable_constraints` **without** `snap`,
exactly as the LTX-2.5 templates do (`dw/variable_constraints.py`).

**Transparent output** — the vendor's literal prompt wrapper:

> `This is an RGBA image with transparency. <your description>. The image has alpha channel and the background is transparent.`

**Prompt-writing convention** (from `prompt_rewrite/prompts/system_prompt_t2i.txt`, the system
prompt of the vendor's own rewriter — this is the closest thing to a MiniMax/LTX-style trained
caption spec):

- Output **English**, whatever the input language.
- **~20 sentences, 400–500 words, ~25 words a sentence.**
- Structure, in order: opening sentence naming medium/style/subject/background/orientation → a
  positional inventory of elements across frame regions → a sequential walkthrough → a dedicated
  text-rendering section if any legible text appears → a dedicated lighting sentence → a closing
  composition summary.
- **Preserve verbatim**: every text string to be rendered, "character for character, in their own
  script, including punctuation and spacing"; every named object, count, stated colour, stated
  position, and the aspect ratio if given.
- **"Observe, don't instruct"** — present tense, third person, no imperatives.
- **Never** include resolution, pixel counts, or quality boosters.
- **"Enumerate; never summarise."**
- Unspecified aspect ratio defaults to 3:2 or 2:3.
- The rewriter emits `{"rewritten_prompt": ..., "wh_ratio": "16:9"}` and the README's own
  integration snippet maps `wh_ratio` through the aspect table to `width`/`height`.

The **edit** rewriter additionally emits `ratio_follow: "<image1>"`, meaning "inherit that input
image's aspect ratio" — which matches the pipeline's own behaviour of deriving `height`/`width`
from the *last* condition image when they are omitted.

The PE models themselves (Qwen3.5-VL 9B, ~20 GB bf16, "a single 40 GB GPU handles either task")
are **too heavy to bundle into a template** on a 24 GB box alongside the generator. The repo's
existing `workflows/templates/expand-prompt.json` / `minimax/enhance-prompt.json` pattern is the
right home if it is ever wanted; the written convention above is the part worth encoding in a
skill or a stored prompt.

## Missing knowledge / open questions

Not answerable from documentation — each needs a real GPU run:

1. **Actual peak VRAM at 2048×2048 with `offload: "model"` on a 24 GB card.** The weight
   arithmetic says 17.5 GB resident; activations at 16 384 target tokens are unknown. This is the
   single most important unknown and it decides whether the flagship template ships at 2K or 1K.
2. **Wall-clock minutes** for the `cost` block. No vendor benchmark, no community number, nothing
   in `jobs.sqlite`. A `cost` entry must be measured (the schema says "Never derived").
3. **Peak VRAM and speed in editing mode with several reference images** — each condition image
   adds a block to the joint sequence and a KV-cache entry across 32 layers.
4. **Whether `transformers` 5.16.1 actually loads the checkpoint.** Vendor asks `>=5.17`. Imports
   succeed; a real `from_pretrained` has not been tried.
5. **Whether RGBA survives the repo's save path end to end** — `content_type: "image/png"` plus
   `embed_metadata`. Plausible from the code, unverified.
6. **Whether `sequential` offload works** at all here (Qwen3-VL is a composite module;
   `exclude_from_cpu_offload` is sequential-only).
7. **Does bnb-4bit quantization of `text_encoder` behave** when that encoder must also run the
   vision tower? No pre-quantized repo exists to test against.
8. **The blog post's benchmark numbers** — `qwen.ai/blog?id=qwen-image-2.1` is JS-rendered and
   returned no text. Any quality claim relative to the 20B is currently uncited.
9. **`use_kv_cache` and the step cache.** The docs say toggling it changes the sample
   bit-for-bit-differently at fixed seed. If a template exposes it, it must be part of the cache
   key — it already is, since it would be a step argument.
10. **Circle / painted-annotation / mask local editing** is advertised but the README shows no
    code for it beyond passing the annotated image as a condition image. Probably just that, but
    unconfirmed.

## What the templates should teach

One idea per template, reading order. `qwen` as the family directory, matching `ltx2/` and
`minimax/`. Every one of these should set `content_type: "image/png"` if alpha is in play and
carry the non-commercial licence note in its `description`.

1. **`workflows/models/qwen-image-2.1.json`** — the flagship, `configures: templates/text-to-image`
   in spirit but with its own argument set (no `guidance_scale`). Teaches: `QwenImage21Pipeline`,
   bf16, `offload: "model"`, 40 steps, an explicit 2K `width`/`height`, guidance left off.
   Declares `variable_constraints` for `width`/`height` on the 32-px grid, no `snap`.
2. **`workflows/templates/qwen/aspect-ratios.json`** — teaches the seven recommended sizes and
   that the pipeline floors off-grid values. Could reasonably be folded into #1 as a documented
   variable rather than its own file.
3. **`workflows/templates/qwen/transparent.json`** — the one idea no other model in the catalog
   has: native RGBA. Teaches the vendor's prompt wrapper *and* `content_type: "image/png"`, which
   is the half that actually preserves the alpha.
4. **`workflows/templates/qwen/edit.json`** — single condition image, instruction prompt, same
   pipeline. Sits beside `templates/image-edit.json` (FLUX.1 Kontext) as the comparison. Teaches
   that `width`/`height` omitted means "inherit the condition image's aspect ratio".
5. **`workflows/templates/qwen/multi-reference.json`** — up to 10 references, following the
   `"image": ["variable:first_image", "variable:second_image"]` list shape that
   `templates/multi-image-reference.json` already established for FLUX.2. Teaches that order is
   semantic (block-causal: later blocks attend to earlier ones) and that the prompt refers to them
   positionally.
6. **`workflows/templates/qwen/true-cfg.json`** — the only template that turns guidance *on*, with
   a `negative_prompt` and `true_cfg_scale > 1`, and says plainly that this doubles the work per
   step and is off by default on purpose. Guards against the next author copying FLUX's
   `guidance_scale: 4`.
7. *(optional, later)* **a prompt-rewriting chain** reusing `templates/expand-prompt` with the PE
   convention written into a stored prompt — only if the 40 GB rewriter can be replaced by an
   instruction to a model already in the catalog.

A `for_each`-driven template is not obviously warranted; this family has no chaining or frame
arithmetic.

## Assessment (under 300 words)

**Yes — onboard it, but ship one template, not six.**

The primary documentation is unusually good for a day-zero release: a full vendor README with a
default-parameter table, an aspect-ratio dict, verbatim code for all three modes, a diffusers docs
page that already exists, and — rarest of all — the vendor's own prompt-rewriter **system prompt**,
which gives a trained-caption spec as concrete as MiniMax's. `QwenImage21Pipeline` is already in
the repo's venv and imports. No engine work is implied.

What I would trust in a template's defaults: the class name and repo id; `torch.bfloat16`;
`num_inference_steps: 40`; `true_cfg_scale` absent (guidance off); the seven aspect-ratio pairs and
the 32-px floor rule; the RGBA prompt wrapper; the list-of-images editing shape; the prompt
convention. All of these are stated by the vendor or readable in the installed source.

What I would **not** ship without a real GPU run: any `cost` entry (there is no number anywhere,
and the schema forbids deriving one); `2048 × 2048` as the default resolution on a 24 GB card —
the weight arithmetic (17.5 GB peak under model offload) leaves ~6 GB for a 16 384-token attention
and I cannot size that from documents, so a first template should probably default to 1K and
document 2K as the vendor's recommendation; anything about `sequential` offload or 4-bit, since no
pre-quantized build exists and the text encoder doubles as the vision tower; and the RGBA→PNG save
path.

Two non-technical flags: the **Qwen Research License is non-commercial**, unlike every Apache-2.0
sibling, and the repo has no convention yet for recording that. And `transformers` is **5.16.1**
against a stated `>=5.17`.

**On a skill**: the draft proposal reserved that question for Qwen-Image-Edit. In 2.1 editing is an
argument, not a checkpoint, so the shape-picking a skill would do collapses to "is there an input
image, and how many". That is template-selection, not a skill — *unless* the prompt convention
(400–500 words, prescribed section order, verbatim text preservation) is judged worth a skill on
its own, the way the LTX-2.5 caption spec was. That is a real argument, and it is the only one.
