## Vendor guidance

- **Recommended sizes (card, GitHub README, diffusers docs; all agree).** "Generally the best results at about 16 MP", effective working range about 4 MP to 20 MP:
  - 1:1: 4096x4096
  - 4:3 / 3:4: 4736x3552 / 3552x4736
  - 3:2 / 2:3: 5024x3360 / 3360x5024
  - 16:9 / 9:16: 5472x3072 / 3072x5472
  - 21:9: 6272x2688 (the portrait swap 2688x6272 is implied by the diffusers docs' "swapped for portrait formats")
  - Other ratios: keep about 16 MP with both sides a multiple of 32 (GitHub README; `size_for()` in `examples/context_ir.py`).
- **Steps and guidance (card; GitHub).** The checkpoint is distilled to 6 sampling steps with no CFG. The hosted API accepts `num_inference_steps` omitted or 6 and `guidance_scale` omitted or 1; other values return HTTP 400. `negative_prompt` is unsupported. The pipeline's own defaults match: no step or guidance input exists at all (see below). `seed` is recommended; the README recommends a CPU generator for reproducibility.
- **Prompt style and length.** "A detailed English description of the whole image" (card). Used as given, truncated to 4096 tokens (card); the README adds that up to 32,000 characters are accepted by the API but content past 4096 tokens is dropped. The diffusers docs: the prompt is used verbatim, no chat template, long complete descriptions work best; an edit prompt names what to preserve, then what to change, then describes the target image in full. GitHub tips: task before style, layout before details; quote text to be rendered with its position and line breaks, or say explicitly that there is no text; exact data with units for charts; grids as rows and columns, not "2x3". Short prompts in other languages should be expanded first (card).
- **Multi-reference editing.** Up to 16 reference images (card, README, blog); the showcase includes a ten-reference example. Upload order defines `<Picture 1>`, `<Picture 2>`, ... in the prompt (card; one-based). Diffusers: pass a list as `image`, a single image is the same path. GitHub tips: give each reference a role and say what changes and what stays. The 16 cap is a vendor statement; the diffusers source enforces no count (grep of the pipeline directory finds none).
- **Prompt enhancer (PE).**
  - Two routes: the hosted `H3-Image-Context-IR` API (`/v1/h3_image_context_ir`, also suggests an aspect ratio), and the local MiniMax-H3-Image-PE (27B, FP4, 17.9 GB per the card; about 18 to 19 GB GPU per the diffusers docs and PE card).
  - PE is text-to-image only; the hosted API always expands edits, and local servers "use the prompt as given" (GitHub README).
  - Local run: SGLang (`sglang>=0.5.23`, `xgrammar>=0.2.7`), or the diffusers blocks `diffusers/minimax-h3-image-pe-blocks`, which **need `trust_remote_code=True`** and `xgrammar` (diffusers docs, PE card). The image model itself needs no `trust_remote_code`; the card does not mention it.
  - PE output is JSON: `expanded_caption` and `aspect_ratio` (T2I). Sampling: temperature 1.0, top_p 0.95, top_k 20, max_tokens 4096, thinking enabled (PE card).
- **Not yet supported (GitHub README):** mask-based inpainting, transparent backgrounds, preview images. Output PNG/JPEG/WebP and 1 to 10 images per request are API features.
- **Card snippet discrepancy [volatile].** The card's example reportedly calls `DiffusionPipeline.from_pretrained(... device_map="cuda")`, while the diffusers docs and the pipeline source are modular-only (`ModularPipeline`, `MiniMaxH3ImageBlocks`). The repo has both `model_index.json` and `modular_model_index.json`. The repo's bench uses `ModularPipeline`; treat the card snippet as unverified here.

## Pipeline facts (diffusers source)

Paths are under `venv/lib/python3.14/site-packages/diffusers/`; diffusers 0.41.0.dev0.

- **Classes.** `MiniMaxH3ImageModularPipeline` (`modular_pipelines/minimax_h3_image/modular_pipeline.py:27`), default blocks `MiniMaxH3ImageBlocks` (`:48`, `modular_blocks_minimax_h3_image.py`), transformer `MiniMaxH3ImageTransformer2DModel`, VAE `AutoencoderKLMiniMaxH3Image`, `MiniMaxH3Scheduler`, text encoder `Qwen3VLForConditionalGeneration`. Two workflows: `text2image` (needs `prompt`), `image_conditioned` (needs `prompt`, `image`).
- **Fixed sampler.** Guidance baked in; no guider, `negative_prompt`, `guidance_scale` or `num_inference_steps` (`modular_pipeline.py:32-36`). Six steps on `sample_sigmas` = [1.0, 0.9675, 0.8875, 0.75, 0.5328, 0.2320, 0.0] (`before_denoise.py:619-626`); the transformer has `num_pdd_heads=6`, one output head per step (`transformer_minimax_h3_image.py`, config docstring near `:422`).
- **Canvas multiple 32.** `canvas_multiple = vae_spatial_compression_ratio (16) * patch_size[2] (2)` (`modular_pipeline.py:68-73`; defaults 16 at `:51-54`, patch `(1, 2, 2)` at `:63-66`). A non-multiple height or width raises `ValueError` in both layout steps (`before_denoise.py:294-298`, `:404-408`). Note that the canvas step rounds the generation canvas itself, so a requested size that is not a multiple of 32 is only refused where the layout steps see the canvas; the repo's `variable_constraints` (modulus 32) refuse it earlier. Reference images need at least 32 px per side (`before_encoder.py:122-124`).
- **`min_generation_area`.** Default `2048 * 2048 = 4194304`; valid range `[1024, 4096 * 4096 = 16777216]`, otherwise `ValueError` (`before_denoise.py:184-193`, `:214-217`). Height and width default to 2048 (`:184-185`). If `height x width` is below the area, both sides are scaled by `sqrt(min_generation_area / (h*w))` at the same aspect ratio and rounded to 32 (`:94-108`), generated on that canvas, then resized back to the requested size after decoding (`decoders.py:95-170`). Consequence: by default a 1024x1024 request is generated at 2048x2048; pass `1024` to always generate at the requested size. The bench did, and a true 1024 pass still took 15.1 s against 2048's 15.2 s (weight-transfer bound), so a smaller canvas saves no time on the offloaded recipe either way.
- **Reference naming.** The prompt refers to them in order as `<Picture 1>`, `<Picture 2>`, ... (`before_encoder.py:92`). Internally each reference gets a text label `Picture {index + 1}: ` (no angle brackets, one-based) followed by `<|vision_start|>`, image pads, `<|vision_end|>`, then the prompt (`encoders.py:240-251`). A single image or a list is accepted (`before_encoder.py:118`).
- **Reference resize rules.** Two copies per reference, via `bound_short_edge` (`before_encoder.py:30-49`): a short edge inside the bounds keeps the original pixels; otherwise it is scaled to the nearer bound keeping ratio, both sides rounded to 32. For the VAE: bounds 1024..2048 (`reference_min/max_short_edge`, `:78-79`). For the text encoder (vision): 1024..1024, so the vision copy is always short edge 1024 (`:80-81`). References are never resized to the output size (`:58-62`). EXIF orientation is applied and the image converted to RGB first (`:120`). Reference rows are held at `t = 0.999` for every step (`modular_pipeline.py:95-98`).
- **Prompt handling.** Verbatim, no chat template, no special tokens, truncated to `max_sequence_length = 4096` tokens, and each reference label is truncated to the same (`modular_pipeline.py:80-83`, `encoders.py:105-111`). `prompt` must be one non-empty string (`encoders.py:225-230`). Conditioning is `hidden_states[50]` of the Qwen3-VL text encoder (`modular_pipeline.py:75-78`).
- **Device and dtype.** The rotary grid is built in float64 and moved through `maybe_adjust_dtype_for_device` (`before_denoise.py:143`, `:319`, `:430`), so mps/xpu fall back from float64. Latents are float32 (`:489`). The transformer keeps `proj_in`, `time_embedder`, `pdd_proj_out`, `rope` in fp32 (`_keep_in_fp32_modules`, `transformer_minimax_h3_image.py:~431`); `_no_split_modules` and `_repeated_blocks` name the block classes group offload splits on. No CUDA-only code was found in the pipeline, but nothing here was run on mps.
- **Sizes and memory.** Diffusers docs: transformer and text encoder about 62 GB each in bf16; do not fit an 80 GB GPU together; auto offload peaks at about 65 GB for 4736x3552.

## Missing knowledge / caveats

- **Licence territory (2026-11-10 licence, read through a fetch summary; re-read the LICENSE file before relying on it).** MiniMax-H3-Image Community License Agreement. Royalty-free, non-exclusive, non-transferable grant to use, reproduce, distribute, modify and make derivatives. The territory is worldwide **except the European Union, the United Kingdom, South Korea and the United States** (Section V.4, which also covers Outputs). Section IV: prior written authorization is required if annualized revenue of you or your affiliates exceeds 1 Million USD, or if you offer a Hosted Service to third parties. Commercial products must display the "MiniMax-H3-Image" name. Outputs may not be used to improve other AI models (V.3) except MiniMax's own. MiniMax claims no rights over Outputs (VI.4). An Acceptable Use Policy (20 items) applies. Hong Kong law. The PE model is covered by the same licence (its base is Apache 2.0). This is not a permissive licence and is more restrictive than the H3 video terms the repo cites; the catalog entry must say so. HF tags it `license:other`.
- **Failure modes are not documented.** No limitations section on the card or the GitHub README beyond the "not yet supported" list. No stated behaviour for faces, text rendering, or more than a handful of references beyond the showcase. No technical report.
- **What the repo's recipe relies on that the vendor does not state** (bench record 2026-11-16/17, `bench/records/h3-image.md`):
  - **SDNQ int8 of the transformer and text encoder.** Never mentioned by the vendor; the vendor's own routes are bf16 on an 80 GB card, or the hosted API. The `modules_to_not_convert` list is read off the transformer, not vendor-supplied. Quality loss from int8 is unmeasured against bf16.
  - **Text encoder borrowed from `MiniMaxAI/MiniMax-H3` at pinned revision `0919fb68`.** The diffusers docs say it is "the same one MiniMax-H3 uses" and that the Hub deduplicates the identical copy; the repo's own 14-shard `text_encoder/` exists, so the borrow is a cache-sharing choice that assumes the two stay identical. If H3 re-uploads its encoder the pin protects the repo but not the claim. The card does not promise the two stay in step.
  - **Truncation to 51 layers.** The pipeline reads `hidden_states[50]` (`modular_pipeline.py:75-78`). It is the repo's inference that 51 layers (not 50) are kept because the HF Qwen3-VL final hidden state has the final norm applied, so the 51st layer's output must exist but not be used as index 50; the vendor states neither the truncation nor its reason.
  - **Group offload.** Block-level for the transformer, leaf-level for the encoder. Vendor never states it; the diffusers docs use `ComponentsManager` auto offload instead. Bench: 63 to 64 GB committed host RAM, ~3.7 to 5.5 GiB VRAM; host RAM is the binding resource, so the family needs a host-RAM requirement in the catalog, not just a VRAM one.
  - **2048 not 16 MP.** The bench ran 2048x2048 (the pipeline default, 4 MP, the bottom of the vendor's 4 to 20 MP range). The vendor's best size is about 16 MP. No 16 MP run has been measured here on 24 GB cards; the diffusers docs' peak of ~65 GB is for auto offload on an 80 GB card. Time per pass was 15.2 s at 2048 and, at 1024 with `min_generation_area=1024`, 15.1 s, which says the offloaded run is bound by weight transfer; 16 MP cost is unmeasured and should not be extrapolated. The 2026-11-17 record is the only measurement.
  - **Vendor speed claims are hosted-API claims.** "4K in under 10 seconds" (blog, 2026-11-11) is about hosted serving. The bench's 2.0 min warm at 2048 is an offloaded 24 GB card figure; the two are not comparable.
  - **The 16-reference cap is unexercised.** The bench used three references.
- **PE with the repo.** `trust_remote_code` is needed only for the diffusers PE blocks. Whether the repo runs PE at all is a trust-gate decision for later, not for the first templates. The edit-PE weights are not released.
- **Card vs docs snippet mismatch** (see Vendor guidance) and **volatility**: the card changed on 2026-11-16 and the GitHub repo had 5 commits, 1 open issue and 2 open PRs on 2026-11-17.
- Not found: reference-count limits in source, a safety or watermark setting, any statement on the SDNQ/quantized paths, and release dates for PE beyond the HF API timestamps.

## Assessment

The vendor is unusually consistent across the card, the GitHub README and the diffusers docs: six steps, no guidance, no negative prompt, about 16 MP as the target, thirty-two-pixel canvas, detailed English descriptions, and references named by upload order as `<Picture N>`. Those are all confirmed by the pipeline source, which makes the engine-facing facts firm: no step or guidance variables, a modulus-32 constraint on width and height, and a `min_generation_area` knob that quietly upscales small requests. The weakest part is not the model but the repo's recipe, which departs from every vendor route (int8 SDNQ, a borrowed pinned text encoder, 51-layer truncation, group offload, 2048 instead of 16 MP) and rests on one bench run of three jobs, with host RAM near 64 GB committed as the real cost. The sharpest catalog risk is the licence: the territory exclusion (US, EU, UK, South Korea) and the 1M USD revenue and hosted-service authorization are not in any other family the repo ships. A user-facing entry should state them before the first run. The templates should therefore teach only what the vendor demonstrates and the bench measured: a plain text-to-image run at the pipeline default and a multi-reference edit. PE, 16 MP sizes and ratios beyond 1:1 are real but unmeasured on 24 GB and should stay as later templates.

## What the templates should teach (reading order)

One idea per template, taken from the vendor's own examples (`examples/t2i.py`, `examples/edit.py`, `examples/reference1.png`, and the diffusers docs).

1. `text-to-image` (the baseline): one detailed English prompt, `width`/`height` as multiples of 32 (default 2048, the pipeline's own), no steps, guidance or negative prompt (fixed checkpoint). Teach `min_generation_area` once (pass `1024` to get a true small canvas) and the vendor size list as the upper end of the range, not the default.
2. `multi-reference`: 1..N references (vendor cap 16; bench exercised 3) named `<Picture 1>`..`<Picture N>` in upload order, in the prompt. A single-image edit is a list of one. Prompt shape from the vendor: what stays, what changes, then the full target description; each reference given a role. References keep their own size (resized only outside a 1024..2048 short edge), so the output size is chosen separately.

Future only (not for the first two templates):

- A size ladder for the vendor's 16 MP list, once a 16 MP run is measured on the 24 GB card class.
- `text-in-image`: quoted text with position and line breaks, from the README tips and the showcase `text.jpg`.
- `chart-or-infographic`: exact data with units, grids as rows and columns.
- `edit-remove-or-swap` from `examples/edit.py` ("keep everything in `<Picture 1>` as it is, but remove ..."), as a single-reference worked case of 2.
- `prompt-expansion` with MiniMax-H3-Image-PE (SGLang or the `trust_remote_code` blocks), after a trust-gate decision.
- A bf16 or larger-card variant of the recipe if the vendor or community publishes quantization guidance.
